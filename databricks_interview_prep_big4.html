// Cheat Sheets

Non-overlapping, one card per topic. Skim these right before the call.

Narrow vs Wide Transformations

  • Narrow — output partition depends on 1 input partition. map, filter, union. No shuffle.
  • Wide — depends on multiple partitions. groupBy, join, distinct, repartition. Triggers shuffle → network I/O, disk spill, stage boundary.
  • Perf impact: more wide transforms = more stages = more shuffle = slower job. Minimize by filtering early, using broadcast joins for small tables.

Spark Spill

  • Happens when a task's in-memory data (shuffle/aggregation buffer) exceeds executor memory → spills to disk.
  • Spark UI signal: Stage detail page shows "Spill (Memory)" / "Spill (Disk)" columns.
  • Fix: increase spark.executor.memory, reduce partition size (more partitions), salt skewed keys, use broadcast join, enable AQE.

Delta MERGE INTO (upsert/SCD2)

MERGE INTO target t
USING source s ON t.id = s.id
WHEN MATCHED AND s.hash != t.hash
  THEN UPDATE SET *
WHEN NOT MATCHED
  THEN INSERT *
For SCD2: matched → close old row (set end_date, is_current=false) instead of overwrite, then insert new version.

Z-Order vs V-Order vs Partitioning

  • Partitioning: physical folders by low-cardinality column (date). Enables partition pruning; too many small partitions → small-file problem.
  • Z-Order: co-locates related data across files for multi-column data skipping (good on high-cardinality filter columns).
  • V-Order (Fabric/Databricks): writes Parquet with special sorting/encoding so downstream Power BI/DirectLake reads are faster — a write-time optimization, not a query hint.
  • Rule of thumb for 10TB: partition by date (coarse), Z-Order on 1–3 frequently filtered columns within partitions.

Medallion Architecture

  • Bronze: raw, as-is, append-only, schema-on-read.
  • Silver: cleaned, deduped, conformed, business keys enforced — engineers treat this as source of truth because it's validated but not yet aggregated/opinionated like Gold.
  • Gold: aggregated, denormalized, consumption-ready (star schema, BI).

Column-Level Security / PII Masking

  • Unity Catalog: CREATE MASKING POLICY or dynamic views with CASE WHEN is_member('pii_group') THEN col ELSE 'MASKED' END.
  • Custom-UDF approach (your CV): apply masking function at ingestion/write time when catalog-native masking isn't available or when policy needs custom logic (hashing, partial masking).
  • Trade-off: catalog-native masking = centrally managed, works for anyone querying; UDF-at-write = simpler but bakes the decision in at write time.

Watermarking (Structured Streaming)

  • Tells Spark "how late is too late" — withWatermark("event_time","10 minutes").
  • Used with windowed aggregations to bound state size; anything later than watermark is dropped (or side-outputted).
  • Late data beyond watermark → route to a dead-letter/late table instead of silently dropping, if correctness matters.

Self-Hosted IR vs Azure IR

  • Azure IR: fully managed, public network, for cloud-to-cloud movement.
  • Self-hosted IR: installed on-prem/VM, needed when source is behind firewall / on-prem (e.g. on-prem SQL Server, SharePoint on private network).
  • Security: self-hosted IR needs outbound-only connectivity setup, node redundancy for HA; Azure IR relies on Azure's managed network + private endpoints/VNET integration for security.

Spark & PySpark Core

EasyTransformation vs Action?
Transformations (select, filter, map, join) are lazy — build a logical plan. Actions (show, count, collect, write) trigger execution of the DAG.
EasyWhat is lazy evaluation and why does Spark do it?
Spark delays execution until an action is hit so it can build an optimized physical plan (Catalyst optimizer) across the whole chain — predicate pushdown, combining narrow transforms into one stage — instead of executing each line eagerly.
MediumExplain data skew — symptoms and 3 fixes.
Uneven key distribution across partitions → a few tasks take far longer than others (visible in Spark UI as long-tail task duration, executor idle time). Fixes: salting the skewed key with a random suffix and exploding the small side, broadcast join if one side is small, repartition on a better key, or enable AQE skew join optimization (auto-splits skewed partitions in Spark 3+).
MediumHow would you handle late-arriving data in a PySpark structured streaming pipeline?
Define a watermark on event time (withWatermark) sized to your acceptable lateness; do windowed aggregation with that watermark. Data arriving after the watermark is dropped by default — if you can't afford to lose it, write a parallel "late arrivals" sink (foreachBatch capturing rows older than watermark) and reconcile downstream, or use Delta MERGE to correct Gold-layer aggregates when late data does arrive.
HardSpark job that normally runs 40 min is now taking 4 hours — walk me through your diagnosis order.
1) Spark UI → find the slow stage, check for skew (task duration variance) and spill (memory/disk spill columns). 2) Check shuffle read/write size — did upstream data volume spike? 3) Check for a cartesian/exploding join (row count blowup mid-DAG). 4) Check cluster health — are executors being killed/restarted (check event log for executor loss)? 5) Check if a broadcast join silently stopped being broadcast (table grew past autoBroadcastJoinThreshold). 6) Only after isolating the cause, apply the fix (repartition/salt/broadcast/cache) — don't just "throw more cluster" at it without knowing why.
BrutalTwo jobs reading the same Delta table concurrently — one is a batch overwrite, one is a streaming reader. What can go wrong, and how do you design around it?
Delta's transaction log gives ACID at the table level but a streaming reader tracks its own read progress via the log; a concurrent overwrite (not append/merge) rewrites files and can break the stream's file tracking or cause it to reprocess/duplicate if not handled via ignoreDeletes/ignoreChanges options, or fail outright with a "files were deleted" error. Design: avoid full overwrites on tables with active streaming readers — use MERGE/append patterns instead, or explicitly set the stream's `ignoreChanges` option knowing it changes exactly-once semantics into at-least-once for changed rows.

Delta Lake

EasyDelta Lake vs Parquet?
Parquet is a file format only — no transaction log, no ACID, no schema enforcement across writes. Delta = Parquet files + a JSON/checkpoint transaction log giving ACID, time travel, schema enforcement/evolution, and support for concurrent reads/writes.
MediumDescribe ACID properties in Delta Lake with an example.
Atomicity: a MERGE either fully commits or not at all (no partial writes) — tracked via the transaction log's commit JSON. Consistency: schema enforcement rejects a write that violates the table's schema. Isolation: concurrent writers use optimistic concurrency control — a conflicting concurrent commit fails and retries rather than corrupting data. Durability: once committed to the log, the write survives failures since it's persisted to cloud storage.
MediumWhen would you use Delta Live Tables (DLT) over a standard Spark notebook pipeline?
When you want declarative pipelines with built-in data quality expectations (@dlt.expect), automatic dependency/DAG management between Bronze→Silver→Gold tables, automatic retries, and managed incremental processing — instead of hand-writing orchestration and manual checkpointing. Trade-off: less granular control than hand-rolled notebooks, and a bit of a learning curve/lock-in.
HardHow do you ensure data quality between Bronze and Silver?
Explicit validation layer: schema/type checks, null checks on business keys, referential checks against dimension tables, row-count reconciliation vs source, duplicate detection on business key + hash of tracked columns. Failing rows get quarantined to a "reject" table with a reason code rather than failing the whole batch. Track pass/fail metrics per run for trend monitoring (a sudden jump in rejects = upstream schema/data problem).
BrutalDesign a Bronze table strategy that has to support both daily batch loads and near-real-time streaming from the same source, without duplicating logic or data.
Use Delta's unified batch+streaming API on one Bronze table: streaming writer does structured streaming appends with checkpointing; batch backfills/reprocessing use the same Delta table with idempotent writes keyed on a natural dedup key (source_id + ingestion_timestamp) so re-running batch for a historical date doesn't duplicate what streaming already wrote. Silver layer's MERGE (keyed on business key + max(event_time)) naturally absorbs whichever arrives — batch or stream — as the same logical upsert, so downstream doesn't need to know which path the row came from.

Unity Catalog & Governance

EasyWhat's the 3-level namespace in Unity Catalog?
catalog.schema.table — catalog is the top-level container (often maps to an environment or business unit), schema = database, table = the object. This lets one metastore govern multiple catalogs with isolated permissions.
MediumHow do you implement column-level security in a Lakehouse?
Unity Catalog column masks/row filters defined via SQL (ALTER TABLE ... SET MASK) that evaluate the querying user's group membership and return masked/null for unauthorized users — enforced centrally regardless of which tool (notebook, BI, SQL warehouse) queries the table. Alternative for engines without native support: dynamic views with CASE-based masking, or masking at write time via UDF (less flexible — one mask for everyone).
MediumHow do you manage secrets/credentials securely in Databricks?
Azure Key Vault-backed secret scope — dbutils.secrets.get(scope, key) — so secrets never appear in notebook code or logs; access to the scope itself is controlled by Databricks ACLs, and the underlying values live in Key Vault (rotated centrally, audited via Key Vault logs).
HardHow would you prove to an auditor that PII was actually masked for every query, not just the ones you tested?
Point to centrally-enforced Unity Catalog masking policies (not per-notebook logic) — since the mask lives on the table object, it applies to every access path (SQL warehouse, notebook, BI tool) and you can show the policy definition + Unity Catalog audit logs proving no user without the entitlement group ever received unmasked values. This is exactly why catalog-native masking is generally preferred over UDF-at-write for anything audit-sensitive — a UDF only protects the one pipeline that calls it, not other consumers of the raw table.
BrutalA data scientist needs row-level access to only their region's data across 40 tables, and requirements change monthly. How do you avoid rewriting 40 view definitions every time?
Externalize the entitlement mapping into a small control table (user/group → allowed region list) rather than hardcoding in the view SQL. Write one row-filter function referencing that control table (is_account_group_member combined with a lookup), attach it as a Unity Catalog row filter to all 40 tables. Changing access = updating the control table, not touching 40 view definitions — governance change becomes a data change, not a code deployment.

Azure Integration & Orchestration

EasyWhat are the core components of ADF?
Pipelines (containers of activities), Activities (the actual work, e.g. Copy), Datasets (schema/location pointers), Linked Services (connection info), Triggers (schedule/event), Integration Runtime (compute that executes the activity).
MediumHow do you handle incremental loads using MERGE in Delta Lake?
Track a high-watermark (last modified timestamp or CDC sequence) per source; pull only rows changed since the last successful run into a staging table; run MERGE INTO target USING staging keyed on business key, updating matched rows and inserting new ones; on success, advance the watermark (store it in a control table, not just "now()" — use the max value actually processed, to be safe against clock skew).
MediumHow do you troubleshoot a bottleneck in an ADF Copy Activity?
Check the Copy Activity's monitoring detail: DIU (Data Integration Unit) usage, parallel copy count, and where time is spent (source read vs sink write vs data movement). Common fixes: increase DIUs, enable parallel copy, check if the source (e.g. on-prem via self-hosted IR) is the actual bottleneck (network/VM sizing) rather than ADF itself, switch to staged copy (via Blob) for cross-region transfers.
HardHow do you handle schema evolution in Bronze/Silver without breaking downstream Power BI reports?
Additive changes (new column) flow through automatically via mergeSchema but Gold/serving views should explicitly SELECT named columns (not SELECT *) so a new column doesn't silently appear/break a report expecting a fixed shape. Breaking changes (renamed/retyped column) should go through a versioned view or a deliberate migration window communicated to BI consumers — never let a schema change flow straight to a live Power BI dataset without a contract/versioning layer in between.
BrutalSource API fails intermittently (roughly 1 in 20 calls) inside an ADF pipeline feeding a Databricks job. Design the end-to-end resilience strategy.
At the ADF Copy/Web activity: retry policy with exponential backoff (not fixed interval, to avoid hammering a struggling API) and a max retry cap; on exhausted retries, activity fails into a documented "partial success" branch rather than failing the whole pipeline. Downstream Databricks job must be idempotent (MERGE-based, not blind append) so a retried/partial batch doesn't create duplicates. Add a reconciliation job comparing source record counts vs landed counts, and alert (not silently continue) if a gap persists beyond a threshold, with checkpointing so a re-run resumes from the last successful point, not from scratch.

Performance & Optimization

EasyWhat is a broadcast join and when do you use it?
When one side of a join is small enough to fit in executor memory (default threshold ~10MB, configurable), Spark ships a full copy to every executor instead of shuffling both sides — avoids the shuffle entirely, much faster. Use for dimension-vs-fact joins where the dimension is small.
MediumHow do you choose between partitioning and Z-Ordering for a 10TB dataset?
Partitioning is coarse and physical — best for a low-cardinality column that's always in the filter (date). Over-partitioning (e.g. by customer_id with millions of values) causes a small-file explosion and slow metadata ops. Z-Ordering is for higher-cardinality columns you filter/join on frequently, applied within partitions — it doesn't create physical folders, just co-locates data in files for better data-skipping. Practical approach: partition by date, Z-Order by 1–3 other hot filter columns, and re-run OPTIMIZE ZORDER periodically as new data lands.
HardExplain Adaptive Query Execution (AQE) and name 3 concrete things it changes at runtime.
AQE re-optimizes the physical plan mid-execution using actual runtime statistics instead of only static estimates. Three things it does: (1) dynamically coalesces shuffle partitions if they turn out too small, (2) dynamically switches a sort-merge join to a broadcast join if a table turns out smaller than expected after filtering, (3) dynamically splits skewed partitions in a join to avoid one task dominating runtime.
BrutalYour daily Gold aggregation job costs 3x more compute than it did 6 months ago, but data volume has only grown 20%. How do you find and fix the real cause?
Don't assume — compare Spark UI/job history metrics month-over-month: shuffle read/write bytes, spill, number of stages, and cluster utilization (are executors idle waiting, i.e. over-provisioned, or maxed out, i.e. under-provisioned?). Common real causes at this magnitude: (a) upstream schema drift added columns that are now unnecessarily carried through wide shuffles, (b) a join that used to be broadcast now exceeds the threshold as one side quietly grew, (c) accumulated small files in Bronze/Silver making scans slower (check if OPTIMIZE/VACUUM has been running), (d) a well-meaning code change added a .cache() or repartition that's now counter-productive. Fix only after the metric comparison points to a specific stage — resist the urge to "just add more cluster."

Data Modeling & Architecture

EasyStar vs Snowflake schema?
Star: denormalized dimensions, fewer joins, faster for BI queries — generally preferred in Big-4 reporting projects. Snowflake: normalized dimensions (less redundancy, more joins) — better for storage efficiency and complex hierarchies, less common in BI-serving layers.
MediumSCD Type 2 — explain with a use case, and how you'd implement it with Delta MERGE.
Keeps full history of dimension changes (e.g. employee changes department) by inserting a new row with a new surrogate key and closing the old row's validity window (end_date, is_current) instead of overwriting. Implementation: MERGE with two WHEN MATCHED branches conceptually — first pass closes changed current rows, second pass (or a UNION staging trick) inserts new versions; many teams do this as two MERGE/INSERT statements in one transaction rather than a single MERGE, since native MERGE can't easily insert-and-update the same logical row in one WHEN clause.
HardDesign a pipeline processing 1TB/day end-to-end (Azure/Databricks stack).
Source systems → ADF (orchestration, incremental extract via watermark) → ADLS Gen2 Bronze (raw, partitioned by ingestion date) → Databricks/Spark (validation, dedup, conform) → Delta Silver (business-key MERGE, SCD2 where needed) → Delta Gold (star schema aggregates) → Power BI / Synapse serving layer. Optimization levers: incremental loads (never full reprocess), autoscaling job clusters, partition + Z-Order strategy on Silver/Gold, DQ gates between each layer, and a control/metadata table driving the whole thing generically (config-driven pipelines rather than one notebook per source).
BrutalFinance says yesterday's Gold-layer revenue number doesn't match the source system by 2%. Walk me through your root-cause process, end to end.
Work backwards through the medallion layers, not forwards: (1) reconcile Gold aggregate against Silver — is it an aggregation/join fan-out bug? (2) reconcile Silver against Bronze — row counts and a hash-based diff on key columns, to catch a dropped dedup or a bad MERGE match condition. (3) reconcile Bronze against source — did the ADF watermark miss a late-changed record, or did a retry double-count via non-idempotent load? Check the transaction log / job run history for that specific date to see if a job was manually re-run or partially failed. Only once the layer is isolated do you look at the specific transformation logic in that layer — this ordered, layer-by-layer reconciliation is the actual skill being tested, not a guess at the bug.

// Hands-On Coding

Easy

Find and remove duplicate rows, keeping the latest by updated_at

WITH ranked AS (
  SELECT *,
         ROW_NUMBER() OVER (
           PARTITION BY business_key
           ORDER BY updated_at DESC
         ) AS rn
  FROM staging_table
)
SELECT * FROM ranked WHERE rn = 1;
This is your dedup-before-MERGE pattern — say this out loud if asked "how do you dedupe intra-batch changes."
Medium

Second highest salary per department

SELECT department_id, employee_id, salary
FROM (
  SELECT department_id, employee_id, salary,
         DENSE_RANK() OVER (
           PARTITION BY department_id ORDER BY salary DESC
         ) AS rnk
  FROM employees
) t
WHERE rnk = 2;
Use DENSE_RANK (not ROW_NUMBER) so ties for 1st place don't accidentally make the 2nd row someone tied for 1st.
Medium

Running total of daily ingested rows per feed

SELECT feed_name, load_date, row_count,
       SUM(row_count) OVER (
         PARTITION BY feed_name
         ORDER BY load_date
         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_total
FROM ingestion_log
ORDER BY feed_name, load_date;
Hard

Gaps-and-islands: find consecutive date ranges of "success" status per pipeline

WITH flagged AS (
  SELECT pipeline_id, run_date, status,
         ROW_NUMBER() OVER (PARTITION BY pipeline_id ORDER BY run_date)
         - ROW_NUMBER() OVER (PARTITION BY pipeline_id, status ORDER BY run_date) AS grp
  FROM pipeline_runs
  WHERE status = 'SUCCESS'
)
SELECT pipeline_id, MIN(run_date) AS island_start, MAX(run_date) AS island_end
FROM flagged
GROUP BY pipeline_id, grp
ORDER BY pipeline_id, island_start;
Classic trick: the difference between two row-number sequences is constant within a consecutive run — that constant is your grouping key.
Brutal

Write the SCD2 close-and-insert as one atomic statement pattern (MERGE-based)

MERGE INTO dim_employee AS t
USING (
  SELECT s.*, 
         CASE WHEN t2.emp_id IS NOT NULL AND t2.row_hash != s.row_hash
              THEN 'UPDATE' ELSE 'INSERT' END AS action
  FROM staging_employee s
  LEFT JOIN dim_employee t2
    ON s.emp_id = t2.emp_id AND t2.is_current = true
) AS src
ON t.emp_id = src.emp_id AND t.is_current = true AND src.action = 'UPDATE'
WHEN MATCHED THEN
  UPDATE SET t.is_current = false, t.end_date = current_date();
-- second statement (Delta MERGE can't insert+update the same key in one pass cleanly):
INSERT INTO dim_employee
SELECT ... FROM staging_employee s
LEFT ANTI JOIN dim_employee t
  ON s.emp_id = t.emp_id AND t.is_current = true AND t.row_hash = s.row_hash;
Be upfront in the interview that native MERGE struggles to update+insert the same logical entity in a single pass — showing you know the limitation is worth more than a "perfect" one-liner.

Highest salary per department (DataFrame API)

result = (

from pyspark.sql.utils import AnalysisException

def read_with_drift_handling(path, expected_schema, spark):
    df = spark.read.option("mergeSchema", "true").parquet(path)
    incoming_cols = set(df.columns)
    expected_cols = set(expected_schema.fieldNames())

    new_cols = incoming_cols - expected_cols
    missing_cols = expected_cols - incoming_cols

    if new_cols:
        # additive drift -> allow, log for schema registry update
        print(f"New columns detected, allowing: {new_cols}")
    if missing_cols:
        # backfill missing expected columns as null to keep contract stable
        for c in missing_cols:
            df = df.withColumn(c, F.lit(None))

from pyspark.sql.functions import col, lit

def explode_bom(bom_df, root_items_df, max_depth=15):
    """
    bom_df: parent_material_id, child_material_id, qty
    root_items_df: material_id (top-level items to explode)
    """
    current_level = (
        root_items_df
          .withColumnRenamed("material_id", "parent_material_id")
          .withColumn("level", lit(0))
          .withColumn("path", col("parent_material_id").cast("string"))
    )
    result = current_level
    depth = 0

    while depth < max_depth:
        next_level = (
            current_level.alias("cur")
              .join(bom_df.alias("bom"),
                    col("cur.parent_material_id") == col("bom.parent_material_id"))
              .select(
                  col("bom.child_material_id").alias("parent_material_id"),
                  (col("cur.level") + 1).alias("level"),
                  F.concat(col("cur.path"), F.lit(">"), col("bom.child_material_id")).alias("path")
              )
        )
        if next_level.limit(1).count() == 0:
            break  # no new rows joined -> stop condition
        next_level = next_level.cache()   # cut lineage growth each iteration
        result = result.unionByName(next_level)
        current_level = next_level
        depth += 1

    return result

def retry_with_backoff(max_retries=5, base_delay=1):
    def decorator(fn):
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):
            for attempt in range(max_retries):
                try:
                    return fn(*args, **kwargs)

                    if attempt == max_retries - 1:
                        raise
                    delay = base_delay * (2 ** attempt) + random.uniform(0, 1)

def flatten_json(obj, parent_key="", sep="."):
    items = {}

        for k, v in obj.items():
            new_key = f"{parent_key}{sep}{k}" if parent_key else k

Design a small config-driven ingestion framework (class hierarchy) — the "why did you choose this approach" question in code form

from abc import ABC, abstractmethod
from dataclasses import dataclass

@dataclass
class SourceConfig:
    name: str
    path: str
    format: str
    watermark_col: str | None = None

class BaseIngestor(ABC):
    def __init__(self, config: SourceConfig):
        self.config = config

    @abstractmethod
    def read(self, spark): ...

    def validate(self, df):
        if df.rdd.isEmpty():
            raise ValueError(f"{self.config.name}: empty batch, aborting load")
        return df

    def run(self, spark):
        df = self.read(spark)
        df = self.validate(df)
        return df

class CSVIngestor(BaseIngestor):
    def read(self, spark):
        return spark.read.option("header", True).csv(self.config.path)

class ParquetIngestor(BaseIngestor):
    def read(self, spark):
        return spark.read.parquet(self.config.path)

# adding a new source type = one new subclass, zero changes to orchestration
INGESTOR_REGISTRY = {"csv": CSVIngestor, "parquet": ParquetIngestor}
This is literally the "onboarding 100+ tables faster" story in code — new source = new small class or config row, not a rewritten pipeline.
