01

Storage Layer

The interview question underneath most storage questions is: "do you understand why the lake needs a table format, not just files?"

Amazon S3

  • Backbone of the lake — durable object store, not a filesystem; eventual consistency issues are gone since 2020 (S3 is now strongly consistent).
  • Storage classes matter for cost questions: Standard → Intelligent-Tiering → Standard-IA → Glacier Instant/Flexible/Deep Archive.
  • Partitioning by high-cardinality, query-filtered columns (e.g. date=) avoids the "small files problem" and keeps Athena/Glue scan costs down.
  • S3 Lifecycle rules automate tiering; Multipart upload for large files; Transfer Acceleration for cross-region ingest.

Delta Lake on S3

  • Databricks stores every managed table as Parquet files on S3 plus a _delta_log transaction log — that log is what gives you ACID transactions on an object store.
  • Solves S3's "no atomic rename" problem: writers commit via the log, not by moving files, so concurrent jobs don't corrupt tables.
  • Time travel (VERSION AS OF), schema evolution, and MERGE INTO (upserts) are the three answers interviewers want to hear when asked "why Delta over plain Parquet".
  • OPTIMIZE + ZORDER BY compacts small files and co-locates related rows — the direct fix for the small-files problem above.
Medallion architecture — the pattern almost every Databricks-on-AWS shop uses and almost every interviewer asks about. Bronze = raw, append-only, schema-on-read from S3. Silver = deduplicated, conformed, type-cast, joined at the grain the business understands. Gold = aggregated, business-level tables that feed BI and ML. Say it in terms of who reads each layer: bronze is for engineers replaying history, silver is for analysts/other pipelines, gold is for dashboards and executives.

File formats

Parquet is default (columnar, compressed, predicate pushdown). Avro for row-oriented streaming/schema registry use cases. ORC shows up mostly in legacy Hive/EMR shops.

Partition strategy

Partition by date/region for pruning; avoid over-partitioning (too many tiny partitions) which slows metadata listing on both S3 and the Glue Catalog.

Unity Catalog volumes

Unity Catalog "Volumes" govern non-tabular files (images, PDFs) on the same S3 buckets, with the same lineage and access control as tables — a common 2025+ interview add-on.

02

Ingestion & Streaming

Know the batch vs. streaming decision cold, and know which AWS service hands off to which Databricks feature.

AWS-native ingestion

  • DMS (Database Migration Service) — CDC out of RDS/Aurora/on-prem DBs into S3 as Parquet/CSV; the standard "how do you get OLTP data into the lake" answer.
  • Kinesis Data Streams / Firehose — real-time event ingestion; Firehose can buffer straight into S3 on a size/time trigger.
  • Glue crawlers — infer schema from S3 and populate the Glue Data Catalog automatically.
  • AppFlow — no-code SaaS connectors (Salesforce, Zendesk) landing directly to S3.

Databricks-native ingestion

  • Auto Loader (cloudFiles) — incrementally and idempotently discovers new files landing in S3, using S3 event notifications via SQS instead of expensive full-bucket listing.
  • Structured Streaming reads directly from Kinesis or Kafka (MSK) with checkpointing to S3 for exactly-once semantics.
  • Delta Live Tables (DLT / Lakeflow Declarative Pipelines) — declarative pipeline definitions with built-in data quality expectations, replacing a lot of hand-rolled Glue ETL.
  • Lakehouse Federation — query RDS/Redshift live via Unity Catalog without a separate ingest job, for smaller or ad-hoc sources.
Interview framing: "We use DMS for CDC out of the OLTP layer and Kinesis for clickstream, both landing raw in S3. Auto Loader then picks those files up incrementally into Bronze Delta tables — so AWS owns getting bytes into S3, and Databricks owns turning those bytes into governed, ACID tables." That single sentence answers "how do the two platforms divide responsibility" cleanly.
03

Processing & Compute

This is where most "AWS vs. Databricks" trick questions live — interviewers want to see you're not treating them as interchangeable.

AWS Glue ETL / EMR

  • Glue Jobs run serverless Spark (or Python Shell / Ray) billed per DPU-hour — good for scheduled, moderate-complexity ETL with no cluster to manage.
  • EMR gives full control over the Spark/Hadoop cluster (instance types, Spot mix, bootstrap actions) — used when you need custom libraries, YARN tuning, or non-Spark engines (Hive, Presto, Flink).
  • Glue Studio's visual editor and job bookmarks (incremental processing) come up often in "how do you avoid reprocessing" questions.

Databricks compute on AWS

  • Databricks control plane is SaaS; the data plane — the actual EC2 instances, EBS volumes, and VPC — runs in your AWS account. This "your data never leaves your VPC" point is a common security-round talking point.
  • Photon is Databricks' native-code vectorized query engine (C++, not JVM) — the direct answer to "why would Databricks Spark outperform EMR Spark on the same instance type."
  • Job clusters (ephemeral, spun up per job, terminate after) vs. all-purpose clusters (interactive, shared, stay warm) — cost and use-case tradeoff interviewers probe.
  • Cluster policies + autoscaling + Spot instance mixes control cost the same way EMR Spot fleets do, but managed through Databricks' own scheduler.

04

Orchestration

Expect a "walk me through a failed pipeline at 3am" question — orchestration and retries are where that story lives.

Step Functions

State-machine orchestration across Lambda, Glue, EMR, and Databricks Jobs API calls — good when a pipeline spans many disparate AWS services.

Amazon MWAA

Managed Apache Airflow; DAG-as-code, the most common answer when a team already has Airflow experience and wants complex dependency graphs and backfills.

Databricks Workflows / Jobs

Native orchestration for notebooks, DLT pipelines, and JARs with built-in retries, alerting, and lineage — often replaces Airflow entirely for lakehouse-only pipelines, invoked from Step Functions/MWAA when it needs to fit a bigger AWS pipeline.

Trigger pattern to know: Step Functions/MWAA calls the Databricks Jobs API (or the run-now REST endpoint) as a task, polls for completion, and branches on success/failure — this is the standard way to keep Databricks as the compute engine while AWS-native tools own cross-service orchestration and alerting (SNS, CloudWatch).
05

Governance & Security

Senior-level interviews spend real time here — access control design signals maturity more than any Spark trivia.

AWS-side controls

  • IAM roles + bucket policies gate raw S3 access; instance profiles let a Databricks cluster assume an IAM role without embedding keys.
  • Lake Formation adds column/row-level permissions on top of the Glue Catalog for services that read via Glue (Athena, Redshift Spectrum, EMR).
  • KMS for encryption at rest (S3-SSE-KMS), VPC endpoints to keep S3 traffic off the public internet, VPC peering/PrivateLink for the Databricks control-plane connection.

Unity Catalog

  • Single governance layer across every workspace: catalogs → schemas → tables/views/volumes/models, with column masking and row filters.
  • Centralized lineage (table- and column-level) generated automatically from query history — a strong differentiator to name versus Glue Catalog, which stores metadata but not lineage natively.
  • Audit logs of every query/grant, delivered to a system table or exported to CloudWatch/S3 for SIEM ingestion.
  • Storage credentials + external locations map Unity Catalog objects back to specific S3 paths/IAM roles — the actual bridge between AWS IAM and Databricks-side grants.
If asked to design access control end-to-end: "IAM/instance profiles authenticate the cluster to AWS; Unity Catalog authorizes which principals can see which catalog/schema/table/column once inside Databricks; Lake Formation covers anything reading the same S3 data through Athena or Redshift Spectrum outside Databricks." That layering — infra auth vs. data authz vs. non-Databricks consumers — is the answer interviewers are fishing for.
06

Warehousing & Serving

Know when data leaves the lakehouse for a warehouse, and when it doesn't need to at all.

Amazon Redshift

MPP columnar warehouse; Spectrum queries S3 directly without loading. Redshift Serverless removes cluster sizing for spiky BI workloads.

Amazon Athena

Serverless, pay-per-TB-scanned SQL over S3 via Presto/Trino — best for ad-hoc/exploratory queries against the Glue Catalog, not sustained BI traffic.

Databricks SQL

SQL warehouses (serverless or classic) query Delta tables directly with Photon — increasingly replaces a separate warehouse entirely, avoiding the ETL hop of copying gold tables into Redshift.

"Why would you still use Redshift if Databricks SQL exists?" — a real interview question. Good answer: legacy BI tools with tighter Redshift connectors, existing heavy investment/skills in Redshift, or workloads needing Redshift-specific features (materialized views with automatic rewrite, RA3 managed storage tiering) — otherwise Databricks SQL against gold Delta tables avoids duplicating data and keeps one governance layer.

System Design Drill

Prompt: "Design a pipeline that ingests clickstream + orders data and serves a near-real-time revenue dashboard, on AWS with Databricks as the processing layer."

01

Clarify SLAs first

Ask: how "near real-time" — seconds, minutes? Peak events/sec? This decides Kinesis shard count and whether you need streaming vs. micro-batch.

02

Ingest

Clickstream → Kinesis Data Streams. Orders (OLTP/RDS) → DMS CDC into S3 raw. Both land as append-only files in an S3 raw/landing prefix.

03

Bronze

Auto Loader picks up the DMS files; Structured Streaming reads Kinesis directly — both write append-only Bronze Delta tables with ingestion metadata (source, load timestamp).

04

 

04

Silver

Streaming job dedupes clickstream on event_id + watermarking for late data; joins orders CDC to get current-state order records via MERGE INTO. Data quality expectations (DLT) drop/quarantine malformed rows.

05

Gold

Aggregate revenue by minute/hour into a Gold Delta table, partitioned by date, exposed through Unity Catalog with row-level security if revenue is region-restricted.

06

Serve

Databricks SQL warehouse (serverless, auto-suspend) powers the dashboard directly off Gold — skip a Redshift hop unless BI tooling requires it.

07

Orchestrate & observe

Databricks Workflows runs the DLT pipeline continuously; CloudWatch + Databricks system tables track lag, failed rows, and cluster cost; SNS alerts on job failure.

08

Name the tradeoffs unprompted

Streaming cluster cost vs. micro-batch every 5 minutes; exactly-once complexity vs. accepting rare duplicates with idempotent downstream writes; single lakehouse copy vs. a Redshift copy for isolation from ad-hoc analyst queries.

Behavioral Prep

Data engineer loops usually include one round on judgment and collaboration, not just systems. Prep a real story for each.

Tell me about a pipeline that broke in production. Want: detection method (alerting, not a user complaint), root cause, the fix, and the follow-up guardrail (test, monitor, schema check) you added.
Describe a time you pushed back on a requirement. Want: you understood the business need, explained the technical/cost tradeoff plainly, and reached a decision — not just "I said no."
How do you decide between a quick fix and the "right" fix under deadline pressure? Want: explicit tradeoff reasoning and evidence you circled back to pay down the shortcut.
Tell me about a disagreement with a data scientist or analyst over a table's grain or definition. Want: you treated the metric definition as a governance problem, documented it (ideally in Unity Catalog comments/lineage), not just resolved it verbally.
How do you approach cost control on a Databricks/AWS bill that's grown unexpectedly? Want: specific levers — job vs. all-purpose clusters, Spot mix, S3 storage class lifecycle, right-sizing DPUs/instance types, auto-termination.
