D1
What makes Delta Lake ACID compliant when the underlying storage (S3/ADLS) is just object storage with no transactions?
Easy▼

Delta Lake never mutates existing Parquet files. Every write (insert, update, delete, merge) creates new Parquet files, and a single JSON commit file in _delta_log/ atomically records "these files are now part of the table, these old ones are removed." That commit file write is the atomic operation.

  • Atomicity — the JSON commit either lands fully or not at all; readers never see a half-written commit.
  • Consistency — schema/constraint checks happen before the commit is accepted.
  • Isolation — optimistic concurrency control: two writers can start at the same version, but the second to commit must detect conflicts against the log and either retry or fail.
  • Durability — once the commit JSON is durably written to cloud storage, the transaction is permanent.
Anchor line: "In my PII masking and SCD-2 pipelines, I relied on this - a failed MERGE never leaves a half-updated table because the commit is all-or-nothing."
D2
Walk me through what's actually inside _delta_log and how a reader reconstructs table state at version N.
Medium▼

Each write produces a numbered JSON file (000000000000000N.json) containing action records: add (new file added, with stats), remove (file logically deleted - tombstoned, not physically deleted immediately), metaData (schema/partitioning changes), commitInfo, and protocol (reader/writer version requirements).

Every 10 commits, Delta writes a checkpoint (a Parquet snapshot of the log state) so readers don't have to replay hundreds of JSON files from scratch - they read the nearest checkpoint at or before N, then replay only the JSON files after it.

To reconstruct version N: start from last checkpoint at or before N, apply add/remove actions from subsequent JSON commits in order, and the resulting live file list is the table at version N.

D3
How does Delta time travel work, and how would you use it to recover from a bad MERGE that ran an hour ago?
Medium▼

Because old data files aren't deleted immediately (only tombstoned in the log), you can query a prior version directly:

-- by version
SELECT * FROM my_table VERSION AS OF 128;

-- by timestamp
SELECT * FROM my_table TIMESTAMP AS OF '2026-07-03T09:00:00';

-- restore the whole table (writes a new commit, doesn't rewrite history)
RESTORE TABLE my_table TO VERSION AS OF 128;

For recovery: first diagnose using DESCRIBE HISTORY my_table to find the version right before the bad MERGE, validate with a VERSION AS OF SELECT, then run RESTORE TABLE. This is much faster than restoring from a backup because the files already exist - restore just rewrites the log pointer.

Catch: time travel only works within the retention window. VACUUM physically deletes tombstoned files older than the retention threshold (default 7 days) - after that, time travel to an older version fails even though log metadata may still reference it.
D4
You ran VACUUM with a 0-hour retention override to save storage cost, and now a long-running streaming read fails with "file not found." Explain why, and how you'd prevent it.
Hard▼

A streaming reader (or a long batch job, or a concurrent time-travel query) holds a snapshot of the table that references specific Parquet files as of the version it started reading. If VACUUM with a very short/zero retention runs concurrently and physically deletes files that are tombstoned but still referenced by that in-flight read, the reader gets "file not found" mid-stream.

Prevention:

  • Never override retention below the default 7-day delta.deletedFileRetentionDuration in production without a very good reason - it exists specifically to protect concurrent readers/time-travel.
  • If you must vacuum aggressively for cost, coordinate a maintenance window and confirm no long-running streams/batch jobs are mid-read.
  • Databricks blocks retention below 168 hours unless you explicitly disable the retention duration check - treat that override as a loud warning sign in any code review.
D5
Schema enforcement vs schema evolution - define both and when each kicks in.
Easy▼

Schema enforcement is Delta's default, protective behavior: a write is rejected if the incoming DataFrame's schema doesn't match the target table (extra columns, mismatched types, missing non-nullable columns). This is what stops a malformed source file from silently corrupting a curated table.

Schema evolution is the opt-in override that lets a write actually change the target schema - most commonly adding new columns - instead of failing.

# enable evolution for one write
df.write.format("delta").mode("append") \
  .option("mergeSchema", "true") \
  .saveAsTable("silver.esg_data")

# or session-wide for a notebook
spark.conf.set("spark.databricks.delta.schema.autoMerge.enabled", "true")

For MERGE statements specifically, you need WITH SCHEMA EVOLUTION (SQL) or the mergeSchema option so new source columns get added to the target automatically.

D6
Your schema-drift framework (from your CV) handles 10+ source feeds. What's the actual failure mode you're guarding against, and how does mergeSchema differ from what you built manually?
Hard▼

The naive failure mode: a source system adds a column, renames a column, or changes a type (e.g., an ID field silently switches from int to string in the source), and a rigid ingestion job throws an AnalysisException mid-run, or worse, an implicit cast corrupts data instead of failing loudly.

mergeSchema only handles the additive case safely (new nullable column appended to target). It does NOT handle: column renames (looks like a drop + add), incompatible type narrowing (e.g. string to int), or reordering - those still need custom logic.

A real framework typically does more than mergeSchema:

  • Diffs incoming schema against the registered/expected schema per source before writing
  • Classifies the diff: additive (safe, auto-evolve) vs breaking (quarantine + alert)
  • Logs the schema version change for audit (this is exactly the IPE documentation angle from your CV)
  • Applies explicit casting rules rather than relying on Spark's implicit casting
This is your strongest CV story - be ready to describe the diff logic in your own PySpark, not just cite mergeSchema as the whole answer.
D7
Explain Unity Catalog's three-level namespace and why it matters compared to the old Hive metastore.
Medium▼

Unity Catalog namespace is catalog.schema.table - an added top level above the Hive metastore's schema.table (database.table). The catalog level lets you cleanly separate environments or business domains (e.g. prod.esg.tcfd_data vs dev.esg.tcfd_data) inside one metastore instead of relying on naming conventions.

Bigger picture: UC is a workspace-independent, account-level metastore. Permissions, lineage, and audit logs are centralized and consistent across every workspace attached to it, whereas Hive metastore was per-workspace, so cross-workspace governance meant duplicating grants everywhere.

D8
How did you actually implement PII masking at Unity Catalog level with custom UDFs? Walk through the mechanism.
Medium▼

Two common UC-native approaches, worth knowing both even if your framework used one:

  • Column masking functions: register a SQL/Python UDF, then attach it to a column via ALTER TABLE ... ALTER COLUMN ssn SET MASK mask_ssn_udf. UC evaluates the mask at query time based on the caller's group membership - someone in a pii_readers group sees plaintext, everyone else sees the masked UDF output.
  • Row/column-level dynamic views: a view wraps the base table with a CASE WHEN is_member('pii_readers') THEN col ELSE mask(col) END expression, and only the view is granted to consumers.
CREATE FUNCTION mask_email(email STRING)
RETURNS STRING
RETURN CASE WHEN is_account_group_member('pii_readers')
            THEN email
            ELSE regexp_replace(email, '(^.).*(@.*$)', '$1***$2') END;

ALTER TABLE silver.hr_data ALTER COLUMN email SET MASK mask_email;

This is enforced centrally at the catalog level - any tool querying through Unity Catalog (notebook, SQL warehouse, Power BI via UC) respects the same mask, so you don't re-implement masking per consumption layer.

D9
Two pipelines concurrently MERGE into the same Delta table's different, non-overlapping partitions. Will both succeed? What if they touch overlapping rows?
Brutal▼

Delta uses optimistic concurrency control (OCC), not row-level locking. Both writers read the table version at start, do their work, then at commit time Delta checks whether the files they read/modified were changed by someone else's commit in between.

Non-overlapping partitions/files: Delta's conflict detection is file-level. If the two MERGEs genuinely touch disjoint files, the second commit succeeds because there's no overlap - Delta detects this via add/remove action comparison against the log, not manual partition math.

Overlapping rows/files: the second committer detects that files it read have since been removed/changed by the first commit, throws a ConcurrentAppendException or ConcurrentDeleteReadException, and must retry - re-read the new version and redo the MERGE. Delta itself does not silently merge the two writers' changes; the losing writer's job needs retry logic.

If asked "how do you handle this in production" - mention job-level retry with exponential backoff around the MERGE call, not just "Delta handles it."
D10
Your DDL auto-generation script provisions 100+ Delta tables from CSV/Parquet schemas. What breaks this approach, and what safeguards did you (or should you) add?
Brutal▼

Naive schema inference from CSV/Parquet is fragile in specific, predictable ways:

  • Type inference drift - a numeric-looking column with one blank/text row in a sample can infer as string instead of double, silently changing the DDL from run to run if inference is re-triggered.
  • Column name collisions with reserved words / invalid characters - spaces, dots, or Delta-reserved characters in CSV headers need sanitization before CREATE TABLE.
  • Precision loss - Parquet's stored type may not map 1:1 to the desired Delta type (e.g., timestamps without timezone vs with).
  • Partition column selection - auto-generation needs an explicit rule (config-driven, not purely inferred) for which column(s) to partition by.

Safeguards: a config/mapping file that pins expected types per known source (not blind inference every run), a dry-run mode that prints the generated DDL for review before executing, and idempotency - re-running the generator against an existing table should diff and evolve, not drop/recreate.

S1
What is Spark Structured Streaming's core model - "streaming as an unbounded table"? Explain simply.
Easy▼

Structured Streaming treats a live data stream as a table that keeps growing - new rows keep getting appended to an unbounded input table. You write a normal batch-style DataFrame query against it, and Spark incrementally re-runs that logic on each new micro-batch of rows, producing an incremental result table that gets written to the output sink.

This means the same DataFrame/SQL API works for batch and streaming - you don't learn a separate streaming DSL like you would with raw Kafka consumers.

S2
What is Auto Loader and how is it different from just using Structured Streaming's file source?
Medium▼

Auto Loader (cloudFiles format) is Databricks' optimized incremental file ingestion connector. The plain Structured Streaming file source does a directory listing on every trigger to find new files, which gets slow and expensive as file counts grow into the millions.

Auto Loader instead tracks new files via cloud-native notification services (S3 event notifications + SQS, or ADLS event grid) instead of repeated listing, so discovery cost stays roughly constant regardless of how many files already exist in the directory. It also has built-in schema inference and evolution for the ingestion layer.

df = (spark.readStream.format("cloudFiles")
      .option("cloudFiles.format", "csv")
      .option("cloudFiles.schemaLocation", "/mnt/schema/ingest_x")
      .option("cloudFiles.inferColumnTypes", "true")
      .load("s3://bucket/raw/source_x/"))

(df.writeStream.format("delta")
   .option("checkpointLocation", "/mnt/checkpoints/ingest_x")
   .trigger(availableNow=True)
   .table("bronze.source_x"))
S3
When would you use COPY INTO instead of Auto Loader?
Easy▼

COPY INTO is a simple, idempotent, SQL-based batch load command - good for smaller, less frequent file drops (thousands of files, not millions) where you don't need continuous/near-real-time ingestion or complex schema evolution tracking. It's re-runnable: files already loaded are tracked and skipped automatically.

COPY INTO bronze.source_x
FROM 's3://bucket/raw/source_x/'
FILEFORMAT = CSV
FORMAT_OPTIONS ('header' = 'true', 'inferSchema' = 'true')
COPY_OPTIONS ('mergeSchema' = 'true');

Auto Loader wins at scale (huge file volumes, needs directory listing avoidance) and when you want a continuously running streaming job rather than a scheduled batch trigger. Rule of thumb they may expect: COPY INTO for simpler/smaller/less frequent, Auto Loader for high-volume/continuous.

S4
Explain watermarking in Structured Streaming and why it's needed for stateful aggregations.
Hard▼

In event-time based windowed aggregation (e.g., "count events per 5-minute window based on event_time, not arrival time"), Spark must keep state for a window open until it's sure no more late-arriving data will show up for it - otherwise it never knows when to finalize and emit results. Left unbounded, that state grows forever.

A watermark tells Spark "I'll tolerate data up to N minutes late; anything later than that, drop it" - which lets Spark safely close and evict state for old windows.

events \
  .withWatermark("event_time", "10 minutes") \
  .groupBy(window("event_time", "5 minutes")) \
  .count()

Trade-off to mention explicitly: a tighter watermark keeps state small and results timely but drops more late data; a looser watermark captures more late data but uses more memory/state and delays final output.

S5
What are Spark Declarative Pipelines (formerly Delta Live Tables / DLT), and what problem do they solve that hand-written streaming jobs don't?
Medium▼

Instead of manually wiring readStream/writeStream, checkpoints, and orchestration between Bronze/Silver/Gold notebooks, you declare each table as a Python/SQL function decorated with @dlt.table, and the framework figures out the dependency graph, execution order, checkpoint management, and incremental processing for you.

import dlt
from pyspark.sql.functions import col

@dlt.table
def bronze_esg():
    return (spark.readStream.format("cloudFiles")
            .option("cloudFiles.format", "json")
            .load("/mnt/raw/esg/"))

@dlt.table
@dlt.expect_or_drop("valid_id", "id IS NOT NULL")
def silver_esg():
    return dlt.read_stream("bronze_esg").filter(col("status") == "active")

It also gives you built-in data quality constraints (@dlt.expect family: warn, drop, or fail the pipeline on violation), automatic lineage visualization, and unified batch+streaming semantics per table without you separately managing triggers.

S6
Compare trigger modes: default micro-batch, fixed interval, Trigger.AvailableNow, and continuous processing. When would you pick each for an ESG-style daily ingestion job?
Hard▼
  • Default micro-batch - runs the next batch immediately after the previous one finishes. Good for lowest achievable latency without continuous mode's constraints.
  • Fixed interval (Trigger.ProcessingTime("5 minutes")) - runs on a schedule regardless of how long the previous batch took (waits if still running). Predictable cadence, useful when downstream systems expect data at fixed times.
  • Trigger.AvailableNow - processes everything currently available then stops, like a scheduled batch job but with streaming's incremental/checkpoint machinery. This is the right fit for your 25-daily-file ESG ingestion: you don't need a cluster running 24/7, so you fire this once a day via a Databricks Job, it drains whatever landed, and shuts down - much cheaper than always-on streaming.
  • Continuous processing - experimental, low-latency (~1ms) mode with a different execution engine; rarely relevant for file-based ESG ingestion, more for true low-latency event processing.
This directly maps to your CV: "25 daily file ingestions across 5 ESG apps" is a textbook Trigger.AvailableNow + Auto Loader pattern, not always-on streaming.
S7
Your streaming job crashes mid-micro-batch after writing some output but before the checkpoint commits. What happens on restart, and how does Delta as a sink guarantee exactly-once semantics here?
Brutal▼

Structured Streaming checkpoints record two things per batch: the offsets read from the source, and (implicitly, via the sink's transaction) whether the batch's output was durably committed. If the job dies after writing data but before the checkpoint's commit log entry for that batch is finalized, Spark treats the batch as not-yet-completed on restart and reprocesses it from the same source offsets.

Because Delta is itself ACID/transactional, re-writing the same micro-batch's output is safe: Delta's streaming sink uses the checkpoint's batch ID to make the write idempotent - it won't double-append the same batch twice, because Delta records which batch IDs have already been committed to that table in the transaction log (txnAppId/txnVersion in the commit metadata). That combination - source-side offset tracking + Delta-side idempotent write on retry - is what gives you exactly-once end-to-end, not just "restart and hope."

W1
How do you call one notebook from another in Databricks?
Easy▼
# from a "driver" notebook
result = dbutils.notebook.run(
    "/Repos/project/etl/silver_transform",
    timeout_seconds=1800,
    arguments={"run_date": "2026-07-04", "source": "tcfd"}
)
print(result)  # value returned by the child's dbutils.notebook.exit()

dbutils.notebook.run() runs the target notebook as a separate job-like execution (its own detached run), waits for it, and returns whatever string the child passed to dbutils.notebook.exit(). Contrast with %run ./other_notebook, which inlines the other notebook's code into the current session (shares variables/context) rather than running it as a separate job - useful for importing shared utility code, not for orchestration.

W2
How does a notebook receive parameters when run as a Databricks Workflow task?
Easy▼
# in the notebook, define a widget matching the job's parameter key
dbutils.widgets.text("run_date", "2026-01-01")
dbutils.widgets.text("source_system", "")

run_date = dbutils.widgets.get("run_date")
source_system = dbutils.widgets.get("source_system")

In the Workflow UI (or the job JSON/DAB YAML), you set base_parameters (or parameters for Python tasks) with key-value pairs. Databricks maps the job parameter key to the widget name automatically when the task runs. Job-level parameters can be overridden per-task, and you can also reference dynamic values like {{job.start_time}} or {{job.trigger.time}}.

W3
How do you pass a value computed in Task A to Task B within the same Workflow (not via a widget/parameter set at job-start)?
Medium▼
# Task A notebook
row_count = df.count()
dbutils.jobs.taskValues.set(key="rows_processed", value=row_count)

# Task B notebook (must list Task A as a dependency in the Workflow)
rows = dbutils.jobs.taskValues.get(
    taskKey="task_a", key="rows_processed",
    default=0, debugValue=100
)

This is Task Values - the mechanism specifically designed for cross-task data passing inside one job run. It only works if Task B has Task A configured as an upstream dependency in the Workflow DAG (so the scheduler knows the order and can resolve the value at runtime). The debugValue is what's used when you run the notebook interactively outside a job context, so your code doesn't break during dev.

W5
What is a Databricks Asset Bundle (DAB), and why would a team move from "REST API scripts" or manual UI job creation to DABs?
Hard▼

A DAB is a YAML-defined, source-controlled representation of your Databricks resources (jobs, DLT pipelines, cluster policies) plus the code they run, deployed via the Databricks CLI (databricks bundle deploy). It's Databricks' answer to "infrastructure as code" for jobs, replacing brittle hand-written REST API scripts or manual UI clicking.

# databricks.yml
bundle:
  name: esg-pipelines

targets:
  dev:
    workspace: {host: https://dev-workspace.databricks.com}
  prod:
    workspace: {host: https://prod-workspace.databricks.com}

resources:
  jobs:
    esg_ingestion:
      name: esg-bronze-to-silver-${bundle.target}
      tasks:
        - task_key: ingest_bronze
          notebook_task:
            notebook_path: ./notebooks/bronze_loader.py
          new_cluster: {spark_version: 14.3.x-scala2.12, num_workers: 2}

Benefits worth naming: environment parameterization (dev/staging/prod from the same definition via targets), the whole job definition lives in Git next to the code so it's reviewable and versioned, and deployment is a single reproducible CLI command that fits directly into a CI/CD pipeline - instead of "someone manually recreated the job in prod and forgot a setting."

Design a Workflow for your ESG monitoring framework: 5 apps, 25 daily files, needs to alert data owners on failure. How would you structure tasks, retries, and alerting?

G2
How do you handle merge conflicts in notebook-based code specifically (as opposed to plain .py files)?
Medium▼

Two layers to this answer:

  • Mechanically: Databricks Repos stores notebooks as source files (.py/.sql with # COMMAND ---------- cell markers, or .ipynb), so standard git diff/merge tooling works, but .ipynb JSON diffs are notoriously unreadable if that format is used - preferring the "source" format (.py with Databricks cell markers) makes conflicts far easier to resolve because it's just text.
  • Process-wise: pull the latest target branch before starting work, keep feature branches short-lived and scoped to one logical change to minimize the surface area for conflicts, and when a conflict does happen, resolve it in an IDE/Databricks Repos UI by understanding both changes' intent (not blindly picking "ours" or "theirs"), then re-test the notebook end-to-end before re-pushing.

If your real answer is "we mostly avoid this because each dev owns separate notebooks/modules," that's a legitimate and honest answer too - say that rather than inventing a conflict-resolution war story you haven't had.

G3
Your DDL migrations go through a release team who raise a PR to deploy - you said you're not fully sure what process they follow. What's the most likely underlying mechanism, and what would you want to find out before this interview?
Hard▼

Most enterprise setups doing this pattern use one of:

  • A schema-migration tool (Flyway, Liquibase, or a custom versioned-DDL-scripts folder) where each DDL change is a numbered, idempotent script; the release team's PR against that migrations repo triggers a CI job that applies pending scripts in order against the target environment, tracking applied versions in a metadata table.
  • A DAB or Terraform-based approach where table/schema definitions are declared as code and a terraform apply / databricks bundle deploy in a CD pipeline reconciles the target environment to match.
  • A simpler manual-gate model: the PR itself is the approval gate, and merging triggers a release pipeline (Jenkins/Azure DevOps/GitHub Actions) that runs the DDL against prod using a service principal with elevated permissions the individual devs don't have - which is often exactly why the release team exists, as a separation-of-duties control for prod schema changes.

Honest framing for the interview: "I write and test the DDL, hand it off with documentation, and the release team owns the deployment gate - likely for separation of duties around prod access. I'd want to understand whether they're using a migration tool or a straight CI/CD trigger, since that affects how I'd write scripts to be safely idempotent." Showing you understand why the separation exists (governance/compliance, matches your IPE/audit documentation work) is worth more than guessing the exact tool.

G4
Why does DDL typically need a separate, more controlled deployment path than regular ETL code changes?
Medium▼

DDL changes are structural and often destructive/irreversible in ways ETL logic bugs aren't: dropping a column loses data permanently, renaming breaks every downstream consumer silently, and changing a type can corrupt existing rows or break constraints. ETL logic bugs usually just produce wrong output that can be rerun once fixed; a bad DDL change can require a restore from backup or Delta time travel to undo, and may have already broken dependent pipelines by the time it's caught.

That's why DDL changes typically need: a separate approval gate (often a DBA/release team, not just the app owner), an explicit rollback script paired with every forward migration, and deployment outside of business hours / with monitoring - none of which is usually required for a routine transformation logic PR.

A1
In Databricks on AWS, what runs on EC2 and what lives in S3?
Easy▼

Compute and storage are decoupled, which is the core of the Lakehouse pitch. EC2 instances are the actual driver + worker nodes of a Databricks cluster - this is where Spark executors run, where compute cost is incurred, and where you choose instance types (e.g. i3.xlarge for I/O-heavy jobs, memory-optimized for large shuffles). Clusters are ephemeral - spun up on demand, auto-terminated when idle.

S3 holds the actual data - Delta Lake table files (Parquet + _delta_log), notebooks (if not using workspace storage), library artifacts, and cluster logs. Because storage is separate from compute, you can shut down every cluster overnight and the data (and its full transaction history) just sits durably in S3, costing only storage, not compute.

A2
How does Unity Catalog manage access to S3 without every user having raw AWS credentials?
Medium▼

UC introduces two objects that sit between users and raw S3 access: a Storage Credential (an IAM role UC's control plane can assume, with trust policy scoped to Databricks' AWS account) and an External Location (a specific S3 path bound to that storage credential). Catalogs/schemas/tables are then created pointing at (or under) an external location.

When a user queries a UC table, Databricks' compute plane requests short-lived, scoped-down credentials from the UC control plane (which assumes the IAM role) rather than the user or cluster having any standing S3 keys. Grants (GRANT SELECT ON TABLE) are enforced at the UC layer before that credential vending even happens - so no direct IAM policy per user is needed; UC becomes the single access-control plane instead of S3 bucket policies.

A3
Explain the difference between a Databricks service principal's IAM role and a group's IAM role. Why would you use one over the other?
Hard▼

Service principal = a non-human identity for automated workloads (a scheduled Job, a CI/CD pipeline, a DAB deployment). It's assigned its own IAM role (via a storage credential) so a production job's data access is tied to the job itself, not to whichever engineer happened to trigger it - critical for auditability ("who/what touched this table" points to a system identity, not a rotating set of humans) and for surviving an engineer leaving the team without breaking prod pipelines.

Group-based IAM role/UC grants = for human users, grouped by function (e.g. esg_data_engineers, pii_readers). You grant catalog/schema/table permissions to the group in Unity Catalog rather than to individuals, so onboarding/offboarding is just an add/remove from the group, not per-person grant management.

Rule of thumb they may want to hear: production pipelines run as service principals; interactive/ad-hoc access is via user groups. Never run a scheduled prod job under a personal user token - that's a classic audit finding.

What is a Kafka topic, partition, and consumer group, in one sentence each?

K3
What's the difference between "at-least-once" and "exactly-once" delivery, and where does Kafka sit by default?
Medium▼

Kafka's default consumer behavior is at-least-once: if a consumer crashes after processing a message but before committing its offset, it will re-read and reprocess that message on restart - safe against data loss, but can create duplicates downstream unless the consumer/sink is idempotent.

Exactly-once semantics require additional machinery: Kafka's transactional producer/consumer APIs on the Kafka side, or - more relevant to your Databricks context - relying on Delta's idempotent streaming sink (checkpoint-tracked batch IDs) so that even if Spark reprocesses the same Kafka offsets after a failure, the write into the Delta table doesn't duplicate rows.

K4
Compare Kafka + Structured Streaming vs. Auto Loader for building the Bronze layer. When would you actually need Kafka rather than file-based ingestion?
Hard▼

Kafka is the right choice when data originates as a genuine event stream with low-latency requirements - application event logs, IoT sensor telemetry, transactional CDC feeds - where sub-second to few-second freshness matters and there's no natural "file" being produced by the source.

Auto Loader/file-based ingestion (your actual ESG use case) fits when the source system's natural unit of delivery already is a file - a nightly CSV/Parquet export, an SFTP/SharePoint drop - and near-real-time latency isn't the requirement. Building a Kafka pipeline to ingest a system that already produces daily CSV files would be needless complexity; you'd be adding a message broker in front of data that's already batch in nature.

If they push on "why don't you use Kafka for ESG," the honest answer is your sources are file-based systems (TCFD, LCA, etc. exporting on a schedule) - Kafka would solve a latency problem you don't have.

Medallion architecture & SCD Type-1 rationale
MED1
For a simple SCD Type-1 lookup table, why bother with Bronze → Silver → Gold at all? Isn't that just 3 copies of the same data wasting storage?
Brutal▼

This is a genuinely good challenge and worth answering with real trade-off reasoning rather than reciting "medallion is best practice." The honest answer has two parts:

1. They're right that storage cost is real, but it's usually the wrong axis to optimize. Cloud object storage (S3/ADLS) is cheap - often fractions of a cent per GB per month - while engineering time spent debugging a mixed raw/curated table, or a compliance failure from ungoverned raw data, is expensive. For a genuinely tiny, stable lookup table (say, a country-code or currency table with a few hundred rows), the medallion pattern is arguably overkill - a pragmatic team might collapse Bronze and Silver for something that small and low-risk.

2. But the value of Bronze isn't "storage of the same data" - each layer earns its keep by adding something the others don't have:

  • Bronze is the immutable audit trail of exactly what the source sent, as-is (even including bad rows). This is what lets you replay history when a business rule changes, and it's your only recovery point if Silver logic had a bug - you reprocess from Bronze instead of re-pulling from a source system that may not retain history.
  • Silver is where SCD-1 dedup/overwrite logic, type casting, and validation actually happen - it's queryable and clean, but still close to source grain, useful for other Silver-to-Silver joins.
  • Gold is business-consumption shaped - aggregated, denormalized, dimension-modeled, matching what a report or another team's SCD-2 fact table actually joins against.

For an SCD-1 lookup specifically, the real question isn't "why 3 copies" but "does this table ever need Bronze's replay capability or Gold's aggregation shape, or is it small/stable enough that Silver alone (with governance/versioning via Delta itself) is sufficient." A senior answer says: "Medallion is a default posture for consistency and governance across the pipeline, not a religious rule - for a trivial static lookup table I'd apply judgment rather than dogma, but I'd still keep at least a Bronze snapshot if the source system doesn't retain its own history, because Delta time travel on a Silver table only protects you from your own bugs, not from the source overwriting its own history before you captured it."

This is the single best question in this whole document to show seniority - most candidates just recite "medallion = best practice," this one rewards actually reasoning about when the pattern doesn't pay for itself.
MED2
What specifically breaks if you skip Bronze and load a source directly into a cleaned Silver-style table?
Medium▼

You lose the raw audit trail - if a transformation bug is discovered a week later, you can't replay the original as-received data to reprocess correctly unless the source system itself retains full history (most operational source systems don't, or purge quickly). You also couple ingestion and transformation into one step, so a schema change or bad row from the source can break the "clean" table directly rather than being caught/quarantined at an earlier, cheaper-to-fix stage. It also removes your ability to reconstruct exactly what a source sent for compliance/audit purposes - directly relevant to your IPE documentation work.

CV3
You built a "recursive BOM hierarchy explosion pipeline using iterative DataFrame joins." Why iterative joins instead of Spark's native recursive CTE-style approaches, and what's the performance concern at 1 crore+ keys?
Hard▼

Spark SQL doesn't support recursive CTEs natively (unlike traditional RDBMSs), so exploding a parent-child bill-of-materials hierarchy (where you don't know the depth in advance) requires an iterative approach: repeatedly self-join the "frontier" of newly discovered children against the mapping table, accumulate results, and stop when an iteration produces no new rows (fixed-point iteration).

Performance concern at 10M+ keys: each iteration is a full join, and if the hierarchy is deep, you pay for N sequential Spark jobs (one per level), each with shuffle cost - this is fundamentally different from a single-pass join. Mitigations worth naming: caching/persisting the accumulating result to avoid recomputing the whole lineage on each iteration, using broadcast joins if the per-level frontier is small relative to the full mapping table, and setting a sane max-iteration safety cap to avoid infinite loops from a cyclic (bad) parent-child mapping in the source data.

Write PySpark that classifies a schema diff between an expected schema and an incoming DataFrame as SAFE (additive) or BREAKING.

def classify_schema_diff(expected_schema, incoming_df):
    expected_fields = {f.name: f.dataType for f in expected_schema.fields}
    incoming_fields = {f.name: f.dataType for f in incoming_df.schema.fields}

    new_cols = set(incoming_fields) - set(expected_fields)
    missing_cols = set(expected_fields) - set(incoming_fields)
    type_changes = {
        col: (expected_fields[col], incoming_fields[col])
        for col in expected_fields.keys() & incoming_fields.keys()
        if expected_fields[col] != incoming_fields[col]
    }

    if missing_cols or type_changes:
        return "BREAKING", {"missing": missing_cols, "type_changes": type_changes}
    if new_cols:
        return "SAFE_ADDITIVE", {"new_columns": new_cols}
    return "NO_CHANGE", {}

Talk through the decision: missing columns or type changes should quarantine + alert (breaking), new nullable columns can auto-evolve safely (additive), and no diff is a no-op. This is the shape of logic your CV's schema-drift framework almost certainly implements.

C4
Write a PySpark function that recursively explodes a parent-child BOM hierarchy into a flat ancestor path table (your CV's BOM pipeline, simplified).

from pyspark.sql.functions import col, lit, concat_ws

def explode_bom(bom_df, root_material_col="material_id",
                 parent_col="parent_id", max_depth=20):
    # bom_df: parent_id, material_id  (self-referencing mapping)
    result = bom_df.filter(col(parent_col).isNull()) \
                    .select(col(root_material_col).alias("material_id"),
                            col(root_material_col).alias("root_id"),
                            lit(0).alias("level"))
    frontier = result

    for depth in range(1, max_depth + 1):
        next_level = (frontier.alias("f")
            .join(bom_df.alias("b"), col("f.material_id") == col(f"b.{parent_col}"))
            .select(col(f"b.{root_material_col}").alias("material_id"),
                    col("f.root_id"),
                    lit(depth).alias("level")))

        if next_level.rdd.isEmpty():
            break

        result = result.unionByName(next_level)
        frontier = next_level.cache()

    return result

Call out the production concerns unprompted: cache the frontier each iteration to avoid recomputation, cap max_depth to guard against a cyclic mapping causing an infinite loop, and mention that at 10M+ keys you'd want to persist/checkpoint intermediate results (or use spark.sparkContext.setCheckpointDir) to avoid an enormous, ever-growing lineage/query plan across many iterations.

def apply_pii_masking(df, sensitive_columns, group_check_expr="is_account_group_member('pii_readers')"):
